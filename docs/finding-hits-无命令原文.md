# Finding：`hits.jsonl` 不留命令原文，导致棘轮在误判上空转

> 状态：**待修**（记录于 2026-07-25，v0.1.10）
> 发现场景：Trellis-Standard 项目连续 6 次 `rm-rf` 命中，全部无法判定真伪
> 本文只记录问题与证据，**不含实现**——修法由维护者定。

---

## ⚠️ 勘误（2026-07-27 · s-40）

**本文原有一处论断是错的，且这个错误比原 finding 本身更值得记住。**

原文多处断言命中「**永远**无法判定真伪」「命令原文不可回溯」，Trellis-Standard 也据此
在 s-29 / s-31 / s-32 / s-34 / s-35 五次会话里对 35 条命中一律「沿先例 dismissed」，
**转化率 0**。

实测：**命令原文一直可回溯**。会话 transcript 完整保存在
`~/.claude/projects/<项目>/<uuid>.jsonl`，而 ratchet 自己生成的会话日志**第 2 行**
就写着 `<!-- transcript:<uuid>.jsonl -->`。按 `hits.at` 的秒级时间戳去 transcript 里
匹配 Bash 工具调用，11 条待处置命中一次还原 10 条，时间戳精确到秒对得上。

还原后的判定结果（这些是原方案永远拿不到的信息）：

| verdict | 数 | 形态 |
|---|---|---|
| confirmed | 6 | push 真推 4 · `rm -rf` 真含 2 |
| **misfire** | **4** | 全部同一形态：heredoc / python 脚本**正文**里的字面量触发规则 |
| undecidable | 1 | 精确秒无匹配 |

**误判率 40%**，且其中一条是 `checkout-discard` 的 `deny`（命令被直接拒，代价远高于 `ask`）。

### 这个错误的教训

「不可判定」是一个**从未验证过的可行性断言**，却被当成既成事实用了五次，
每次都以「同前」结案，于是第 6 次、第 11 次照常发生。
**把没验证的前提当证据用**——这比缺字段本身危害大得多：缺字段只是不方便，
错误的不可行性断言会直接关掉整条调查路径。

下次写 finding 时的硬要求：凡是断言「无法 X」，必须附上**试过并失败的记录**；
只是「没想到怎么做」就写成「做不到」，等于给后来者发了一张假的封条。

### 对下文的影响

- 「修复方向」一节**依然成立**，但理由要换：不是「否则不可判定」，
  而是「否则每次判定都要手工反查 transcript（约 20 行脚本 + 逐条比对）」。
  自动落盘把这个成本降到零，**这仍然值得修**。
- 「为什么不该改去修切词误判」一节**结论不变，且被新证据加强**：
  4 条误判全部是正文字面量触发，正是该节预判的三种形态之一；
  fail-closed 是有意设计，不为少几次误判去放松安全门禁。

## 一句话

`record_hit()` 只写 `rule / decision / at`，**不写触发命中的命令原文**。
于是每次复盘**在 `hits.jsonl` 内部**都回答不了「这次是真拦，还是误拦」，
命中记录退化成一个计数器，`/ratchet:ratchet` 在这类命中上事实上一直在空转。

> 勘误：这**不等于**不可判定 —— 转到 transcript 就能判。见顶部勘误节。

## 证据链

### 1. 代码事实（`bin/ratchet-guard:425-441`）

```python
def record_hit(root: str, rule_id: str, decision: str) -> None:
    """记一笔命中。这是棘爪释放的数据基础 —— 没有命中统计，减法就只能靠拍脑袋。"""
    ...
    line = json.dumps(
        {"rule": rule_id, "decision": decision,
         "at": datetime.datetime.now(...).isoformat(timespec="seconds")},
        ...
    )
```

签名里没有命令文本，调用点 `emit()` 也没往下传——`emit` 拿得到 `reason`，但拿不到原始命令。

### 2. 后果：连续四次「沿先例」定性

Trellis-Standard 的 `.ratchet/hits.jsonl` 里，人工回填的 disposition 原文：

```
s-34 复核：dismissed: guard正常履职；命令原文未留存于hits，
           沿s-29/s-31/s-32先例定性为误判/尽职，无新领域缺口
s-34     ：dismissed: s-34审计grep的搜索模式内含危险字面量，guard按原文匹配误判；
           同s-32类，属ratchet切词实现缺口，不写入领域规则
```

**「命令原文未留存于hits，沿先例定性」** —— 这就是空转的自述。
s-29 / s-31 / s-32 / s-34 四次，每次都在猜，每次都以「同前」结案，
所以第 5 次、第 6 次照常发生。

### 3. 与 ratchet 自身设计意图的矛盾

`ratchet-guard` 顶部注释写道：

> 每条规则带 id —— 命中会被记录，供 `/ratchet:slim` 做减法审计。
> **没有命中数据，减法就只能靠拍脑袋。**

这个判断是对的，但只兑现了一半：**规则命中「数」有了，命中「内容」没有**。
减法（该不该删这条规则）靠计数勉强能做；
而棘轮（该不该为这次命中加约束）**必须知道命令是什么**，计数完全不够。

## 为什么不该改去修「切词误判」

这是本次分析的主要结论，记下来避免维护者走岔路。

6 次命中的实际触发形态：

| 形态 | 例子 |
|---|---|
| grep/搜索模式内含危险字面量 | `grep -n "rm-rf\|rm -rf" bin/ratchet-guard` |
| heredoc 正文内含危险字面量 | 把这条教训写进会话日志时，`<<'EOF'` 正文里出现该字面量 |
| 引号不配平导致无法切词 | 命令里有 `2>/dev/null` 等使 `shlex` 失败的片段 |

guard 在这三种情形下都退回**原文匹配**并拒绝，且提示语已写明理由与出路
（「把它写进文件，再用 `-F <file>` 读入」）。

**这是有意的 fail-closed，不是缺陷**——guard 自己的注释就写着「漏拦远比误拦严重」。
为了少几次误判去放松一个安全门禁，方向是错的。
使用侧的正确应对本来就是改用 Write/Read 工具、或先落文件再引用，属**工作流问题**。

所以要修的不是「别误判」，是**「让人能判定这次是不是误判」**。

## 修复方向（供参考，非强制）

核心只有一件事：**让 `record_hit` 拿到并落盘命令原文**。

需要维护者定的取舍：

1. **脱敏与长度**：命令可能含密钥/令牌。截断到定长（如 200 字符）能降低泄密面，
   但过短会截掉判定所需的上下文。`hits.jsonl` 与 transcript 同级敏感度，可参照其口径。
2. **是否记 `reason` 分支**：guard 对「切词成功」与「退回原文匹配」给的提示语不同，
   把这个分支一并记下，可直接区分「真拦」与「原文误伤」，比事后读命令更省事。
3. **向后兼容**：旧记录没有该字段，`ratchet-audit` 需容忍缺失，不能因此报错。

**回归测试建议**：`test/run.sh` 加一条——构造一个「参数串内含危险字面量」的调用，
断言 `hits.jsonl` 新记录里能取回该命令文本。没有测试的约束不算约束。

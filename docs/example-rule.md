# 未经验证的「事实」，不许写进代码

**能写成校验器的都已经去写校验器了。留在这里的两条，是代码判定不了的行为约束。**

## 一、子代理与搜索给的字段名，必须实测

子代理、WebSearch、文档摘要**会编造字段名、参数名、协议细节**，编得很像真的——有表格、有类型、有默认值。

任何来自它们的 API 字段名 / 配置键名 / 协议细节，写进代码前必须真机验证。验证成本几分钟；错了的成本是整条链路重做。

**溯源**（2026-07-12, s-1）：子代理声称 statusLine 的 stdin 含 `context.tokensUsed / percentUsed`，还给了完整 schema。据此设计了整个上下文报告链路。实测：**这三个字段根本不存在**，只有 `transcript_path`，占比得自己解析 transcript 算。

## 二、你自己的印象，同样是未经验证的来源

上一条防的是别人编。更容易漏的是：**你没读源码，就断言本仓某个组件「是怎么实现的」**——而且说得很笃定。

断言一个组件的实现方式之前，**先读它的源码**。尤其当这个断言会导出一个修改方案时。

**溯源**（2026-07-13, s-3）：commit message 里含 `rm -rf` 字面量被 guard deny。我没读 `bin/ratchet-guard`，就断言「它是纯字符串匹配，不区分命令与引号内文本」，据此提了改进方案，用户批准了。

读源码后：`scan_text()` **本来就会**剔除引号内字面量，注释写得清清楚楚，测试里早有 `expect allow 'git commit -m "fix rm -rf false positive"'`。真实原因是 heredoc 的**有意保守回退**。门禁没坏，是我看错了。

**代价**：照那个方案改下去，就是为一次低频误报，在真危险路径上开洞（`cat <<EOF | sh` 的 heredoc 体会被执行）。

「我知道这段代码怎么写的」是最危险的一种印象——它不像猜测，感觉像记忆。读一遍 30 秒。

# 初始化 ratchet

把脚手架铺到当前项目。**先问清楚，再动手**——档位选错了，用户要么被过度流程拖累，要么保护不足。

## 第一步：判断这个项目该不该装

**简单项目不要装。** 这是最有效的防臃肿措施，也是你该主动说出口的建议。

一次性脚本、单文件工具、几小时就结束的分析任务——装脚手架是自我折磨。如果看起来是这类项目，**直接告诉用户不建议装**，说明理由，让他自己定。

## 第二步：问档位

用 AskUserQuestion 问，别自己猜。两个档：

**普通（standard）** —— 多会话、要留痕、要防危险操作，但没有版本发布节奏。
装：纪律基线 + 起手简报 + 危险动作门禁 + 自动留痕 + 上下文常显。

**复杂（complex）** —— 多月、多迭代、有对外发布。
在普通档基础上，state 里启用 `iteration` / `stage` 字段，配合迭代与阶段管理。

选不准就选普通——档位可以后续升级，一开始就赌重的没必要。

## 第三步：问上下文窗口

这个值**必须问**，不能猜。transcript 里没有窗口信息（实测确认），同一个模型名可能跑在 200k 也可能跑在 1M 上。猜错了，上下文占比会显示成荒谬的数字（这个 bug 真实发生过）。

常见值：`200000`（默认）/ `1000000`（长上下文档位）。

## 第四步：铺

```bash
ratchet-init --preset <standard|complex> --context-window <N>
```

**不要自己用 Write 工具去铺这些文件。** 脚本是确定性的、可测的、幂等的；模型每次"记得铺哪些文件"不是。

## 第五步：自检并汇报

```bash
ratchet-state              # state.json 是否合法
ratchet-brief --check      # 简报是否在 2 KB 预算内
ratchet-overhead           # 机制税体检
```

三条都过了，告诉用户：

- 铺了什么（`.ratchet/` 下各文件的职责）
- **哪些是他的数据（`state.json` / `log/`，plugin 永不覆写），哪些是 plugin 产物（`constitution.md`，upgrade 会更新）** —— 这条边界必须说清楚，否则将来某次 upgrade 会让他以为留痕被抹了
- 机器现在替他管住了什么（危险动作、起手简报、收尾留痕、上下文占比），所以这些**不需要他再用文字规则去要求**

## 第六步：把 state 填上

新铺的 `state.json` 里 `current.task` / `current.next` 是占位符。问用户现在要做什么，填进去——起手简报靠它们工作。

注意字段有长度上限（task/next 各 50 字），**这是 K1 字节预算反推出来的硬约束，不是建议**。写不下说明那是"叙述"，该进日志，不该进 state。

## 已经装过的情况

`ratchet-init --check` 先看现状。已初始化的项目再跑 init 会拒绝覆盖 `state.json`——这是有意的，用户的留痕数据不能被 init 抹掉。

只想更新宪法/模板：`--force`（只覆写 plugin 产物，不动 state 与 log）。

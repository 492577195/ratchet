# 减法：让棘爪松开

棘轮每次失败都加一条永久约束。**它只进不退。** 跑三年就是几百条规则、几十个校验器——规则膨胀 → 上下文稀释 → 注意力分散 → 规则更容易被忽略 → 再加规则。

这正是它本来要治的病。所以棘爪必须能松开。

## 什么时候做

- `ratchet-overhead` 报热区超预算
- 宪法逼近 4 KB
- 用户说"维护这套东西比干活还累"—— **这句话是最强的信号，听到就立刻做**
- 定期（比如每个季度）

## 第一步：拿事实

```bash
ratchet-audit
```

它会给出：硬校验器的命中统计、软规则的体积与年龄、宪法体积、热区占用。

**不要凭感觉做减法。** 没有数据，结论永远是"先留着吧"——这就是臃肿的来源。

## 第二步：按优先级砍

### 1. 软规则 > 硬校验器

这是最重要的一条原则：

- **软规则吃上下文**：每次会话都要读一遍，占注意力预算
- **硬校验器不吃**：它是代码，不进模型的上下文

所以**零命中的硬校验器不必删**——它是廉价保险，留着没成本。要减的是软规则。

### 2. 高频命中的软规则 = 文字管不住它

如果一条软规则反复被违反，说明"写在文字里让模型自觉遵守"这个方案对它无效。

**把它升级成硬校验器，然后删掉原来那条软规则。**

最后半句是关键，最容易漏。留着两份等于白升级——上下文照占，还多了一份维护成本。

### 3. 长期没再犯的规则 = 化石

半年零命中、半年没修改的规则，多半是因为问题已经被工具或流程根治了。规则还在那儿，只是在占用注意力。

**删掉。** 如果真的再犯，棘轮会把它加回来——而且那时加回来的版本会更准确，因为有新的失败案例。

### 4. 宪法条目

`.ratchet/constitution.md` 里，检查每一条：

- 这条已经被某个校验器覆盖了吗？→ 删（校验器已经在管了，文字是重复）
- 这条最近一年真的起过作用吗？→ 想不出具体例子就删
- 这条能改写成校验器吗？→ 能就转，然后删

## 第三步：动手前先问

删规则是有风险的——万一它其实在起作用呢？

所以**列出待删清单给用户看，让他拍板**。用 AskUserQuestion，每条说清楚：

- 规则内容
- 为什么建议删（零命中？已被校验器覆盖？）
- 删掉的风险是什么

不要自作主张删。

## 第四步：验收

```bash
ratchet-audit          # 热区回到预算内了吗
./test/run.sh          # 删规则没删坏东西吧
```

然后告诉用户：减了多少、热区从多少降到多少、**哪些约束其实没有真的消失（只是从软规则变成了硬校验器）**。

最后一句很重要——用户需要知道保护没有变弱，只是换了更可靠的形式。

# 会话交接

**主动的上下文重置，优于被动的自动压缩。**

自动压缩是有损的：它把工具输出、调试轨迹、失败尝试一股脑摘要掉，而摘要器不知道哪些细节是后续要用的。结果是模型在长会话后期开始丢失约束、重复踩坑、目标漂移。

更好的做法是在**你还清醒的时候**，主动把状态写成一份结构化的握手文件，然后物理清空上下文，用它重启。这不是省钱手段，是保持连贯性的手段。

## 什么时候该做

- 上下文占用超过 **60–70%**（状态栏会显示；到 85% 才动手就晚了，那时输出质量已经在下降）
- 一个阶段性任务刚完成，下一个任务方向不同
- 用户明确要求交接

**不要等到模型开始表现出"上下文焦虑"**——那种为了赶紧结束而草率收尾的症状出现时，损失已经发生了。

## 怎么做

### 1. 生成机械部分

```bash
ratchet-digest --transcript <transcript_path> --session <N> --out
```

`--out` 直接落盘到 `.ratchet/log/{今天}-s{N}.md`。**不要自己重定向命名** —— 命名由机制决定，
手工起名会造出 `s-1.md` 这种与 hook 约定分叉的文件（真踩过）。不带 `--out` 只渲染到 stdout。

这会自动抽出：改了哪些文件、跑了哪些关键命令、工具调用统计、token 消耗、上下文占比。**不要手写这些**——它们在 transcript 里已经有了，誊写一遍是浪费推理算力。

（如果会话是正常结束的，SessionEnd hook 已经自动生成过草稿，在 `.ratchet/log/` 下，直接接着写就行。）

### 2. 手写「决策与教训」

这是唯一需要你动脑的部分，**硬上限 1 KB**。只写机器写不出来的东西：

- **为什么这么选**，特别是当时排除了什么、为什么排除
- **哪里判断错了**，错在哪一步的推理上
- **下次别再踩什么**

不要复述机械事实。不要写"完成了 X 功能"这种从文件改动里一眼可见的话。写不满不用凑。

一个好的教训长这样：
> agent 给的 statusLine 字段表是编的（`context.percentUsed` 不存在）。凡是子代理/搜索返回的字段名、协议细节，写进代码前必须实测。

一个没用的教训长这样：
> 遇到了一些问题，通过调试解决了。

### 3. 更新 state

把 `.ratchet/state.json` 更新到「下一个会话睁眼就能接着干」的状态：

- `current.task` / `current.next` —— 下个会话的起点
- `blocked` —— 卡在哪，解除条件是什么（要可判定，不是"等待中"）
- `pending_user` —— 有什么在等用户拍板
- `recent_decisions` —— 最近 3 条，滚动淘汰
- `session.log_written` = `true`

字段都有长度上限，超了 `ratchet-state` 会拒绝。**写不下不是理由去改 schema，是信号说明那段内容属于叙述，该进日志。**

### 4. 校验

```bash
ratchet-state          # state 合法？
ratchet-brief          # 看一眼下个会话睁眼会看到什么
```

**用 `ratchet-brief` 的输出验收自己的交接质量**：如果一个完全没有本次会话记忆的人，只看这份简报无法接着干活，那交接就是失败的。回去补。

### 5. 告诉用户可以清了

明确说：交接文件已就绪，现在 `/clear` 是安全的，下个会话会自动读到简报。
